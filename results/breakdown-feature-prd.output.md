## 1. Feature Name

**Stale-Reference & Path-Consistency CI Guard**

A CI workflow step that fails the build when a PR introduces (or re-introduces) dead internal links or the `Bash/` vs `projects/Bash/` toolkit path mismatch, so the stale references enumerated in the parent Epic cannot quietly return.

---

## 2. Feature Idea (from workspace evidence)

`AGENTS.md §13` (verified, lines 364–381) lists six known-stale-reference categories in the SandBox workspace. The parent Epic resolves them via documentation/CI edits (stories A1–C2). This feature is **D1**: make those fixes durable by adding an automated gate.

Concrete, verified problems this guard must catch (all traced to real files):

1. **Toolkit path mismatch** — `.github/workflows/bash-scripts-ci.yml` line 5 watches `Bash/**`, but the toolkit actually lives at `projects/Bash/` (verified: `projects/Bash/` exists, root `Bash/` does **not** exist). A PR that edits the toolkit at `projects/Bash/` therefore will not trigger the CI job. *Source:* `AGENTS.md §13.2` (line 374–375), confirmed by directory listing.
2. **Dead `Bash/` references in agent instructions** — `.github/copilot-instructions.md` contains **13** references to a nonexistent root `Bash/` (e.g. `Bash/src/`, `Bash/docs/`, `Bash/tests/`, `Bash/package.json`). A guard should fail if any new `Bash/` (non-`projects/Bash/`) path reference is added. *Source:* `AGENTS.md §13.1` (line 369–373), confirmed by `grep` (13 matches).
3. **Dead internal links in root docs** — `README.md` points at a missing `PROJECT_RULES.md` (§13.4), and the prior root `AGENTS.md` pointed at a missing `SOUL.md` (§13.3). A guard should detect markdown links / references to files that do not exist in the repo.

The guard is a **preventive enabler**, not a one-time fix: it converts the Epic's manual remediation into a regression-proof state.

## 4. Goals

- **G1** — CI fails a PR that adds a reference to a nonexistent file (dead internal link) under the watched doc/agent paths.
- **G2** — CI fails a PR that introduces a `Bash/` (root) toolkit path reference instead of `projects/Bash/`.
- **G3** — CI triggers correctly when the toolkit at `projects/Bash/**` is changed (path-filter correctness), so the guard itself runs when relevant.
- **G4** — The check is deterministic, fast (< 60s on a warm runner), and produces an actionable error message naming the offending file and reference.

## 5. Non-Goals (Out of Scope)

- **Not** rewriting the toolkit logic in `projects/Bash/src`. (Epic Non-Goal)
- **Not** fixing the existing 13 stale refs in `copilot-instructions.md` — that is Epic story A1; this feature *guards against their return* once fixed.
- **Not** a full link-graph/spelling linter for the entire repo — only the stale-reference categories enumerated in `AGENTS.md §13`.
- **Not** migrating file layout (e.g. moving `projects/Bash/` to `Bash/`). (Epic Non-Goal)

## 6. Requirements

### Functional

- **FR1 — Dead-link detection.** On pull_request, scan the changed files (and/or the watched paths: `README.md`, `AGENTS.md`, `.github/copilot-instructions.md`, `docs/**`, `agents/**`, `instructions/**`) for markdown links and bare file references whose target does not resolve in the repo. Fail the build and list each dead target with its source file:line.
- **FR2 — Path-mismatch detection.** Detect references matching the pattern `Bash/` that are **not** `projects/Bash/` (e.g. `Bash/src`, `Bash/tests`, `Bash/package.json`). Fail the build and report each occurrence.
- **FR3 — CI path-filter correction.** Update `bash-scripts-ci.yml` `paths:` filter from `Bash/**` to `projects/Bash/**` (line 5) so toolkit edits trigger the job. This is the precondition that lets the guard run on relevant PRs and is itself part of the Epic's M1 exit criterion.
- **FR4 — Clear failure output.** On violation, print a grouped, human-readable report (file:line + the bad reference + the suggested correct form, e.g. `Bash/src → projects/Bash/src`). Exit non-zero so the workflow fails.
- **FR5 — Allowlist / exceptions.** Support an inline allowlist for intentional references (e.g. prose that says "the old root `Bash/` path") so legitimate mentions are not flagged. (Open question — see §9.)

### Non-Functional

- **NFR1 — Performance:** full check completes in < 60s on `ubuntu-latest`.
- **NFR2 — Determinism:** same input → same pass/fail; no network calls (links resolved against the checked-out tree only).
- **NFR3 — Maintainability:** check logic lives in a committed script under `.github/scripts/` (consistent with existing `audit_*.py` / `*.ps1` tooling there) so it can be unit-tested and reused.
- **NFR4 — Conventions:** scripts follow workspace conventions — CRLF line endings (`.editorconfig`), bun as package manager (NOT pnpm, per `AGENTS.md §3` and `packageManager` intent), no `.bak` files (use git).
- **NFR5 — Integration:** extend the existing `validate-readme.yml` workflow (verified present, runs on PR to `staged` branch) OR `bash-scripts-ci.yml`; do not create a redundant standalone workflow unless justified.

## 8. Dependencies & Constraints

- **Existing workflows:** `validate-readme.yml` (PR → `staged`, validates generated files) and `bash-scripts-ci.yml` (path-filtered). The guard likely extends one of these. *Verified both exist.*
- **Existing audit tooling:** `.github/scripts/` already contains `audit_prompts.py`, `audit_agents_hashes.ps1`, `inventory-agents.ps1`, `update_agents_md.py` — the new checker should follow the same script-in-`.github/scripts/` pattern and could reuse path-walking helpers.
- **Constraints:** bun not pnpm; CRLF (`.editorconfig`); no backup files; preserve frontmatter conventions for any touched prompt files.
- **Risk:** the guard runs on every relevant PR, so a false positive blocks merges — the allowlist (FR5) and a dry-run local mode are mandatory to avoid churn.

## 9. Open Questions (clarifying, per prompt rules)

1. **Carry the existing 13 `Bash/` fixes first?** FR2 assumes story A1 has already corrected `copilot-instructions.md`. Should the guard ship *after* A1, or ship in "warn-only" mode alongside A1? (Recommendation: ship after A1; use warn-only during rollout.)
2. **Scope of link scanning** — changed files only, or the full watched path set? Full-set is safer but slower; changed-files is faster but misses edits that move a target file. (Recommendation: scan changed files' references + validate that referenced targets still exist in tree.)
3. **Allowlist mechanism** — inline comment marker (e.g. `<!-- allow-link: Bash/ -->`) vs. a committed `stale-ref-allowlist.json`? Needs owner decision.
4. **Which workflow to extend** — `validate-readme.yml` already runs on `staged` PRs and has PR-comment capability; `bash-scripts-ci.yml` owns toolkit paths. The guard's two concerns may split across both.
